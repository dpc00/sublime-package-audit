# How the audit was done

This is the method as it was used, including the rules that were added after something went wrong.

## 1. Set-up

- Test in **portable copies** of Sublime Text (builds 4200 and 4215), never in the everyday install. A portable copy has its own `Data` folder, so a broken package cannot touch real settings.
- Before each package, **back up** the copy's `Preferences.sublime-settings` and `Package Control.sublime-settings`. After the test, restore them and compare file hashes to prove nothing was left behind.
- The agent drove Sublime through sublime-mcp (an MCP server that runs inside Sublime), reading the editor's own state: tabs, console, scopes, menus, quick panels. A screenshot tool was used to look at the window, and a real pointer click only when the person at the computer had been idle (a rule that was tightened during the audit).

## 2. Choosing packages

Lists were built from the Package Control channel (install rank, date of the last push, amount of Python), then tightened or loosened in steps. `lists/README.md` says what built each list. Archived or long-dead packages were left out: they only cause trouble. Packages that need a paid account or a native dialog that cannot be dismissed were skipped or noted.

## 3. Install like a user

0. **Read the package's repository first — issues *and* pull requests, all states.** Every package, every time, before installing. It says whether the package is already known broken, whether a fix already exists (a closed, unmerged pull request is still a proposed fix), and whether the maintainer accepts reports at all. One repository refused AI-generated contributions outright: the work was good, the pull request was closed, and a later report on the same ground was pure noise.
1. Command Palette, `Package Control: Install Package`, pick the package from the list. Do not copy files by hand unless the package cannot be installed from Package Control; say so in the record when that happens.
2. Wait until Package Control has recorded the package in its settings file. If Sublime is restarted too soon, Package Control removes it as an orphan.
3. **Restart the test copy before judging a package that ships settings or a theme.** Sublime reads a package's own `Preferences.sublime-settings` only at start-up; before the restart every default of that package is missing, and anything that depends on them looks broken.

## 4. What is checked

- The console, for errors at load and when the package is used. Note: a captured console only sees the plugin host it was started in; packages in the other host need the other build or a look at the dialogs.
- Everything the README promises, one claim at a time: commands in the palette, menu items (open the real menu and look; greyed out means the command is missing), key bindings, snippets (type the trigger and press Tab in a file of the right type), completions, settings (does changing it do anything?).
- Syntaxes and color schemes: write a small sample, read the scope under the cursor for each token, apply the scheme and look at it.
- Themes: restart, select the theme, open a few tabs, look at it.
- Static checks that find real mistakes cheaply: undefined and unused variables in schemes and syntaxes, JSON and YAML that parse, referenced files that exist, `ruff` with only the rules for undefined names.
- A package's own syntax tests or examples, when it ships them.

## 5. Proving a finding before reporting it

- Finish the proof. If a cause is suspected, test the fix on a **copy** of the file and see the effect change.
- Rule out your own test artifacts first: a wrong cursor position, a file copied with the wrong encoding, a stray panel that swallowed keystrokes, the missing restart above.
- State plainly what was seen and what was not. If a typo has no visible effect, say so.
- Never file on a guess. Check existing issues first, and file one issue per finding.
- No patches or pull requests unless a maintainer asks.

## 6. Writing the report

- Short and plain. It starts with "omp - deepseek v4 flash reports:" so the maintainer knows an AI wrote it. No greeting, no sign-off.
- Say where (file, line, setting), what happens (with the build and operating system), and a suggested fix in one line.
- Where issues are disabled or the repository is archived, send the same text by email to the maintainer's commit address, and show the owner the exact text first.
- If a maintainer asks for no more reports, there are no more reports.

## 7. Clean up

Remove the package, wait for Package Control's "Removed package" line, close every tab and window the test opened, remove any file the test created, restore the two settings files, quit the test copy, and write the result down. Leftovers from earlier packages cause false findings in later ones.

## 8. Things that fooled the audit
- Sweep wider than the hashes, 2026-11-11. Four baseline files do not cover everything a test leaves in `Data`: that day's residue was `Lib/python314/websocket` + `websocket_client-1.9.2.dist-info` (installed as a library for NinetyFive and surviving the package's removal), `Cache/CodeMap/custom_languages/md.sublime-syntax.cache` (survived deleting `Packages/User/CodeMap`), `hello.exe` (NimPlus compiled `hello.nim`, which was already gone) and `probe/{probe.cr,probe.v,probe.zig}`. Check `Data` itself, `Lib/python314` and `Cache` after every cycle; identify an unknown file by mtime and strings before deleting it.
- Near-miss triage, 2026-11-11. `sweep_cmdtypo_verify_2026_11_11.py` re-checks the rows against each package's CURRENT release and writes `data/command_nearmiss_verified_2026_11_11.tsv` with REGISTERED/MISSING per declared id; run it before treating any row as a defect. Two traps it fixes: `releases[-1]` in the channel JSON is not the newest release (sort by `date` first, or the row describes 1.0.5 of a package now at 1.3.3), and the id must be derived with Sublime's rule - an underscore only before a capital that starts a word (`WPSeekCom` -> `wp_seek_com`, but `Togglefile` -> `togglefile`, and never inside a run of capitals). Of the 34 rows from the 2026-11-10 sweep, 12 are REGISTERED (false positives: Pretty JSON, Toggle File, GitGutter, Package Control, GitSavvy, Merlin, MicroPython Tools, NoDialogs, Django Manage Commands, Highlime, RSL, SublimErl, subversion) and 22 are MISSING across 14 packages, among them the already-filed wpseek (three ids, PR #11) and Translate-CN / NinetyFive (both already reported). A 3.3-host package cannot be judged from the registry at all: `get_commands` reports every id of such a package with `class_names: []` and no module (NimPlus showed ten of them), so `class_names: []` there means "this host did not load it", not "nothing implements it" - the verdict has to come from the zip derivation. That covers most of what is left in the list (AGSBS Markdown Helper, Boo & BooJs, ESpec, MarkLogic, IJulia, subversion).
- Triage of the release list, 2026-11-11. `data/released_since_report_2026_11_10.tsv` holds every release that followed a report, which is 2110 rows and mostly already answered. A candidate is live only if the release postdates **our last comment on the issue**, not the RESULTS row: twice in one session a cycle was spent retesting Joy and Edit Preferences, both already commented fixed. `issue_outcomes_2026_11_10.tsv` is a snapshot and its `updated_at` misses comments made after it was taken, so the shortlist has to be confirmed by reading the issue itself before installing anything.
- Lean pilot, 2026-11-11. Lean 4.35.0 lives at `C:\Users\donal\tools\lean-elan\home\toolchains\leanprover--lean4---v4.35.0\bin\lean.exe`; the elan shim in `home/bin` has no default toolchain, so call the toolchain binary by path. `tools/lean-elan/work/SublimeMcpRanges.lean` models the range clamping in `get_view_chars`: it proves the shipped code always answers `0 ≤ begin ≤ end ≤ size`, and carries a witness that the pre-fix code (clamp `begin` only) reports `begin: -2` for the range measured in the rig. What that buys: universality over inputs for a pure function, at roughly forty lines and several wrong statements before the right one (a swap-symmetry claim was disproved by its own proof and dropped). What it cannot do: anything touching Sublime's API — windows, panels, loading views — where the rig remains the only oracle. `GhostShellSlots.lean` in the same folder is the same method applied to GhostShell's broker slots.
- Before testing a package, read its rows in `RESULTS.tsv` (2026-11-11: Jinja2 was tested a third time in the same day because the candidate list was trusted over the ledger; the retest had to be merged back into the existing row). One row per package per date: a retest replaces it, never adds another.

- `RESULTS.tsv` has two shapes (2026-11-11): rows written from that date on are `package, date, verdict, detail` and the file starts with a header; the ~5,700 older rows are `package, date, prose` with no verdict column. Any whole-file tool must branch on the field count before grouping, or a bulk rewrite will do to one half what the 2026-11-09 incident did to the ledger. Normalising the history is a deliberate pass: backup, dry run, then write.

- The maintainer gate is a judgement, not a stopwatch (Donald, 2026-11-11): the question is "has the maintainer abandoned his work?", so a repo whose last push was a few months ago is still active, and the answer has to come from the project's own shape — release history, issues answered, whether the code is maintained — not from counting days since the last commit. Do not turn it into "no commit in 90 days, therefore ledger only".
- A repo with GitHub issues disabled has no tracker to file in at all; that, not inactivity, is why a finding stays in the ledger in that case.

- Settings of a just-installed package not being read until a restart (above).
- A file downloaded through a PowerShell redirect arrived with a byte-order mark and Windows line endings and the plugin silently did nothing.
- A test that opens a second window or a modal dialog can freeze the editor; do those from a terminal that is not inside the editor.
- GitHub's search API stops at 1000 results and rate-limits quick queries; list issues in small date windows, slowly.
- A "not installable" package (no releases in the channel) cannot be tested by the normal route; copying its files in by hand is the fallback, and the record says so.

- Added 2026-10-16: a package that downloads libraries (ExportHtml) keeps the editor busy for a minute after the "Installed package" line; wait for "Package ... successfully installed" before using it.
- Added 2026-10-16: a file opened right after an install is opened before the package's syntax is indexed (it shows as Plain Text); close and reopen it.
- Added 2026-10-16: a hover popup needs the real mouse pointer over the test window; another window in front blocks it. Making the test window topmost for the one hover (and clearing it after) worked.
- Added 2026-10-16: Sublime's "Syntax Tests" build runs only files named `syntax_test_*` that sit inside the Packages folder; copy a package's test files there (renamed if needed) to run them.
- Added 2026-10-16: a plugin that starts a helper with `pythonw` hides the helper's errors; run the helper script by hand with the same arguments to see them. A third-party Python library the helper needs can be installed into its own folder and given to the test copy only (`pip install --target <folder>` plus `PYTHONPATH` for that one process), so nothing is added to the machine's Python.
- Added 2026-10-16: a plugin command that waits for a helper window (`subprocess.communicate()` on the main thread) freezes the editor until the window closes; close the helper window from outside to recover, and do not run such a command from inside the editor you are driving.
- Added 2026-10-16: when planning which packages are left, match names by prefix against every earlier record ("LSP-Bicep (real .NET 10 test)" is the same package as "LSP-Bicep") and look at all dates, or finished work is planned again.
- Added 2026-10-16: a scope read (get_scope_at_cursor) made in the same batch as goto_line or open_file can return the scope of the OLD position or none; move first, read the scope in a separate call. A captured console does not show Sublime's own syntax load errors.
- Added 2026-11-04: a persistent Python shell that opens a `.sublime-package` with `zipfile.ZipFile()` keeps the file locked after the portable quits. Use `with zipfile.ZipFile(...)` or call `.close()`. Windows Restart Manager (`RmGetList`) names the holding PID; in the 2026-11-04 case it was the Python shell, not the main Sublime, even though the main project had contained the tools folder.
- Added 2026-11-07: removing a package does not purge its modules, and `reload_plugins` does not re-execute a module that is already imported. Every probe-file change (a throwaway linter, a settings file read at import) needs a full restart of the portable, or the old code keeps running and the next observation is a lie. Seen both ways on 2026-11-07: the goto-flash addon appeared to load with SublimeLinter removed (stale module still in `sys.modules`), and a corrected probe linter stayed unregistered until a restart.
- Added 2026-11-07: a SublimeLinter linter registers itself through `LinterMeta` at class creation, but is silently marked `disabled` — and therefore never registered — unless the class supplies `defaults = {"selector": ...}`. A probe linter without that looks exactly like "the package does not work" (`persist.linter_classes` empty, no lint output, no console error).
- Added 2026-11-07: SublimeLinter's diagnostics are inline annotations plus the status bar (`ruff-lsp(w1 e1)`); LSP's own "diagnostics" panel says "No diagnostics. Well done!" regardless, because it only knows LSP's clients. Reading the LSP panel to judge a SublimeLinter linter produces a false negative — take a screenshot instead.
- Added 2026-11-07: a 0.8 s flash or a phantom that disappears cannot be read back after the fact; raise the package's `duration` setting (or equivalent) to something like 30 in `Data/Packages/User/<package>.sublime-settings` before the run, then query `view.get_regions(<the package's own region key>)` straight after the triggering command.
- Added 2026-11-07: when a package's own entry says "Manual only. Not listed on PackageControl" but Package Control *does* install it, that mismatch is usually the finding: an undeclared dependency (SublimeLinter) leaves the plugin failing at import with only a console traceback, filing 2026-11-07 as kaste/SublimeLinter-any-lsp#1 and kaste/SublimeLinter-addon-goto-flash#1.
- Added 2026-11-08: judge the settings by the files, not by the running editor. After a picker removal prints "Removed package" and the in-memory `installed_packages` is already clean, the file on disk can still list the package and `Preferences.sublime-settings` can have gained it in `ignored_packages` (PackageResourceViewer, 2026-11-08: `2aaf53b1…` became `10958a8a…` and `87f3aacc…` became `e7867185…` at exit; xmake the same evening, `c10158d9…` and `37308c86…`). The pattern seen three times on 2026-11-08: quitting within a second or two of the removal line leaves the old entries, while the IndentX round — same picker removal, a longer wait before exit — wrote clean files. So hash both files before quitting, and if they differ, wait and remove again in the same session rather than after a restart. Typing the entries out of the JSON restores both hashes exactly.
- Added 2026-11-08: a package's "Edit Package Resource" leaves a real override folder under `Data/Packages/<Package>/`; that folder is a change to the install and has to be deleted before removing the package and quitting, or the next baseline check fails for a reason that has nothing to do with the package.
- Added 2026-11-09: never rewrite a ledger with a whole-file tool. A script that read `RESULTS.tsv` into rows, regrouped them and wrote the file back turned the "one row per package" rule into a data loss: names like `BinaryPlist fork retest`, `sort-numerically retest` and `ST 4215 portable copy, BuildSock retest` are real package names, so folding every name that ends in " retest" renamed them onto their neighbours, and two further repair passes on top of that produced ten duplicate names. What recovered it was `git checkout HEAD --` plus re-recording only the rows whose evidence was in front of us, and your Drive copies of the two files to confirm the rest. Fold retests by looking at the row's date and evidence, in the editor, with `str_replace_based_edit_tool` — not by matching names in a script.
- Added 2026-11-09: the figures the README can carry are the ones a rule computes. `lines` and `with a conclusion` are one pass each; the untested buckets (102/136/56/97/31/17 on 2026-11-07) came from a review whose classifier was never written down, and re-deriving them by prefix matching gives 87/3/0/24/1/0 — a different question answered. Keep such a figure at the date it was measured and say so, rather than replacing it with a number that looks current and is not comparable.
- Added 2026-11-10: `run_command` runs in the window's **active view**, which is not necessarily the view `get_active_file` reports. Driving a probe that way measured a 3170-character console while the file just opened held 4 characters, and the numbers read like a library quirk. Enumerate instead — `for w in sublime.windows(): for v in w.views(): print(v.file_name(), v.size(), v.sel())` — and `w.focus_view(v)` the one you mean. When the question is an API semantic, do not depend on the active view at all: construct the value in code (`sublime.Region(4, 0)`) and run the package's own command on it.
- Added 2026-11-10: `ui_press_key "shift+left"` did not extend the selection — the region was still empty afterwards, so a command that branches on emptiness took the insert branch and its output (`#46c9e1blue`) was read as the product inserting "in front of" a reversed selection. That produced a filed and later withdrawn report (lindskogen/RandomHEXColor#1). Before concluding anything about selection handling, print `sel()` and check `empty()`; and check the API rather than infer: `Region.begin()` is `min(a, b)` and `Region.end()` is `max(a, b)`, so a hypothesis of the form "the code misreads direction" has to survive that fact first.
- Added 2026-11-10: a `set_file_syntax` naming a resource that does not exist raises a **modal dialog** in the rig window ("Error loading syntax file … Unable to stat …") that blocks the main thread. The dialog text is worth having — it is the same failure a user sees, and it is how the Mint Lang recursion error was captured verbatim — but answer it at once with `dismiss_native_window`, and never leave it up.
- Added 2026-11-10: a `.sublime-package` entry named `con.*` is not filtered at install and not extracted to disk, so the Windows device-name rule that applies to repository files does not apply to a resource path inside the archive (Mint Lang ships `Snippets/con.sublime-snippet` and it installs). Judge such a file by whether Sublime can read it, not by its format: TextMate XML under a `.sublime-snippet` name **does** load (measured 2026-11-10 — unscoped expands anywhere, a `<scope>` is honoured), so the format was never the defect there; that package's real defect was the syntax never loading.
- Added 2026-11-10: two reports went out in one night on a test artifact, both from reading silence as evidence — RandomHEXColor#1 (a selection that had never been made, so the command ran on an empty caret) and Mint Lang#2 (a snippet whose scope could not match because the syntax itself never loads, tested in a Plain Text buffer). Before writing "it does not work", print the state the command branches on, and put the test in a buffer whose scope should match. If the environment cannot express the precondition, the result is no evidence, not a negative.
- Added 2026-11-10: a detector must pass a positive control before its output is read. The `file_extensions` scan returned 331 packages with "no extension on any syntax"; five of the first seven checked by hand (Ballerina, Bend, Carbon, Awk, BoxLang) all declare one. The regex `^\s*file_extensions:\s*(.*)$` let `\s*` swallow the newline, so the value captured was the next line (`- bal`) and the list walk that followed saw nothing. Use `[ \t]` where a newline must not be crossed, and print the parsed result for three known-good files before running over thousands.
- Added 2026-11-10: stop the rig by the PID `Popen` returned, never by image name. `taskkill /F /IM sublime_text.exe` matches every Sublime Text on the machine: it closed the person's own editor and the window hosting the session, and `/F` skips hot exit. What recovers the buffers is `Local\\Auto Save Session.sublime_session` — check its timestamp before reporting a loss.
- Added 2026-11-10, removed-stdlib sweep: "imports a module that Python 3.14 dropped" is not the same as "cannot load". `imp` is **importable** in Sublime's host (`eval_python` → `import imp` succeeds) even though CPython 3.14 removed it, so every `imp` hit is a false positive; the modules that really raise are `distutils`, `lib2to3`, `cgi`, `cgitb`, `telnetlib`, `asyncore`, `asynchat`, `pipes`, `crypt`, `imghdr`, `sndhdr`, `uu`, `xdrlib`, `chunk`, `audioop`, `aifc`, `mailcap`, `sunau`, `nis`, `ossaudiodev`, `spwd`, `msilib`, `nntplib`, `smtpd` — check the host before writing the list. Worse, a static hit says nothing about *when* the import runs: Anaconda's 22 `lib2to3` hits are its own vendored copy inside `nda_lib/autopep/`, imported only when the PEP8 command is used, not at load. Import-time failure has to be measured, not inferred: put the packages in `Packages/`, restart once, and ask the registry which packages contributed no command class at all. Same lesson as the positive control — the detector describes a text pattern, not a failure.
- Added 2026-11-10: check the repository's age before filing, not just its issues page. Three reports went to `cakephp/cakephp-tmbundle` — real defects, all valid — and the maintainer closed every one with "this repository hasn't been updated in 15 years. Instead of spending time on these issues I am going to close them and archive this repository." Nothing in the report was wrong; the targeting was. A package that installs is not a package anyone maintains: look at the last push date first, and treat anything older than a few years as a record for the ledger rather than an inbox for a person. The repo is now on `do_not_file`.
- Added 2026-11-10, syntax-file sweep: PyYAML is stricter than Sublime's own YAML parser, so a `.sublime-syntax` that PyYAML rejects can load perfectly. Verified both ways in the portable: Naomi 4.3.2 ships 460 syntax files whose header is `%YAML1.2` (no space) and its grammars load (`naomi.css3` → `source.css`), and KDL 2.0.7's files, which PyYAML also refused, load as `text.kdl.1`. The sweep counted 948 such rows — every one checked by hand was a false positive. Only `ScannerError`/`ParserError`/`ComposerError` and the two genuine JSON structure errors (CloseTabsLeft, Dumbest Ipsum — both missing braces, both 2015–2016 repos) survived triage. A syntax file's header being wrong to a Python YAML library says nothing about Sublime; load the resource and read `scope_name()` before believing it.
- Added 2026-11-10, command-name detector: `type(name, (sublime_plugin.TextCommand,), {}).__new__(cls).name()` returns exactly what the loader registers, and it settled two of my wrong guesses in a row. The rule it showed: an underscore goes before an uppercase that is **followed by** a lowercase. Three further traps in the same detector, each of which produced a wrong answer first: a class pattern with `\bCommand\b` matches only a bare `Command` base and silently finds **no** classes in classes deriving from `sublime_plugin.WindowCommand` (19 real hits became 0); a class may inherit several bases, so `MpGetFileCommand(WindowCommand, Settings)` must still be counted; and `channel_pc.json` was a stale cache, so half the "bugs" were already fixed in a newer release — refresh `channel_v3.json` before believing a hit. A squashed reference like `togglefile` is **not** an accepted alias for `toggle_file` unless a class of that name exists — NimPlus settled that (its class registers `nim_plus_open_site`, and `nimplus_open_site` was NOT registered). Even so, run the detector against a known-broken package before reading the survivors: on the run that reported zero hits, the zero was the detector's failure, not the packages'.
- Added 2026-11-10, argument-mismatch sweep: reading `run()`'s literal signature is not enough. jfcherng's WindowsContextMenu was flagged for passing `app`/`target` to a `run(self, app_menu_set)`, but the method is wrapped in `@_provide_app_menu_set(...)`, which injects that parameter — a decorator invisible to an AST pass. Of 12 candidates the only real one (Pep's Example.sublime-keymap passing `scope` to `run(self, edit)`) sits on a 2024 repo, so none were fileable. Treat decorator-wrapped and base-class `run()`s as unknown, not as mismatches, and confirm a hit by calling the method with the binding's own args before writing it down.
- Added 2026-11-10, scope measurements: assert the buffer text equals the sample before reading `view.scope_name()`. `run_command('insert')` auto-indents, so a sample pasted that way is not the text under test and its scopes are meaningless — that produced a false "amountless posting is not scoped" reading on sublime-ledger-syntax#3, a bug upstream had already fixed two hours after we filed it. Set `auto_indent` false, insert, compare each line to the intended string, and only then measure.
- Incident 2026-11-10, stale-buffer modal in the rig: after a package was removed from `st_portable`, a view still holding its syntax raised `Error loading syntax file "...TodoReview.hidden-tmLanguage": Unable to stat` as a native modal on the next syntax reload, and the eval call that triggered it timed out with the dialog up. Answering it is not enough: the view re-raises on every reload until the buffer is closed. Close the stale view first, then dismiss, then re-run the step — and treat an MCP timeout as unknown state, checking `list_native_windows` before retrying.
- Rule and procedure 2026-11-11, in Donald's words: "don't use http to the mcp. Don't write scripts unles there is a vital timing issue that you are testing." After launching `st_portable`, check first whether the portable MCP is already mounted (`mcp__sublime_mcp_portable_*` — it often connects by itself); if it is not, enter `/mcp reconnect sublime-mcp-portable` in the GhostShell agent tab, wait, and repeat the check. Rig work then runs only through those tools (extras via `mcp__sublime_mcp_portable_batch`); an HTTP client against 9510 is not tooling, and a script is acceptable only when the measurement itself is a duration. If the tools are still absent after the reconnect, stop and say so.
- Incident 2026-11-11, closing the last window: `window.run_command("close_window")` on the last window quits Sublime Text, and the call does not return while the plugin host shuts down. The bridge waits 5 s on the main thread, then reports "no native dialog or menu is open, so the main thread is busy" with the stack inside `window_run_command` — both wedges on this date (a close issued from eval, and a close issued from the tool before the fix) were this and nothing else. Read that timeout as a quitting app, not as a stuck package or a hidden dialog, and do not
  re-dismiss dialogs that are not there. Fixed in sublime-commander 0a61b95: the last window's reply is sent 300 ms ahead of the close, so the call answers in 0.04 s and the process then exits; closing a window while others remain is synchronous (0.02-0.03 s) and unchanged.
